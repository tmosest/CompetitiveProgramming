The key to avoid duplicate cycles (and visiting the same node again) is to traverse nodes in increasing order. That is, we only do [1, 2, 3] and never [2, 3, 1].

After we identify 3 nodes, we check if there is a connection between the first and last node to count it as a loop.

With this, we can write a DFS solution. However, since we only need to check triplets, three loops will do.

I tried a few container options for edges; adjacency list (backed by a hash set) was fastest for Python, and a boolean adjacency matrix - for C++.

Python 3

class Solution:
    def numberOfPaths(self, n: int, corridors: List[List[int]]) -> int:
        al, res = [set() for _ in range(n + 1)], 0
        for (p1, p2) in corridors:
            al[min(p1, p2)].add(max(p1, p2))
        for i in range(n + 1):
            for j in al[i]:
                for k in al[j]:
                    res += 1 if k in al[i] else 0
        return res

Java

public int numberOfPaths(int n, int[][] corridors) {
    boolean[][] am = new boolean[n + 1][n + 1];
    int res = 0;
    for (var c : corridors)
        am[Math.min(c[0], c[1])][Math.max(c[0], c[1])] = true;
    for (int i = 1; i < n; ++i)
        for (int j = i + 1; j < n; ++j)
            for (int k = j + 1; am[i][j] && k <= n; ++k)
                res += am[j][k] && am[i][k] ? 1 : 0;        
    return res;
}

Intuition

This problem was hard for me. I could figure out that DFS with backedge detection is needed, but went with the general problem instead of simplifying it to the case of 3. The case of 3 is super straightforward. If there are three nodes which form a loop, then we will have first node and last node matching. And that's all.

Another problem I ran into (okay, generic solution should have also worked). But another problem was that I was unable to figure out why the TLE was happening. The TLE was happening on the last test case because we were doing repeated work and time complexity was going above O(n^2) (Basically, it became O(n^3)). This was happening because I was counting the same things again. For example, consider this

1<-->2<--->3
<------->

All nodes are connected, so this is one solution. Right? But what about this one?

3<--->2<---->1
<-------->

We should be counting just one of these, right? But we're going to iterate on both. This was my learning when looking at the solution. Need to make sure I identify this repeated nature, and also need to make sure we resolve it. In this case, the resolution would have been very easy. Just don't process repeated element by either always processing monotonically increasing or decreasing rows. This way, its guaranteed that we only find the solution just once.

Good problem basically. Thanks leetcode.

Approach

  1. Create adjacency list.
  2. For each node, do a DFS
  3. In DFS, add the node only if current index is greater than the previous node. This is to avoid duplicates.
  4. If you find the original node that you would have added once again, then you have an edge, add to the solution.
  5. Return solution count.

Complexity

  • Time complexity: O(n^2)

  • Space complexity: O(K+V)

Code

class Solution {
    private int res = 0;
    public int numberOfPaths(int n, int[][] corridors) {
        HashSet<Integer>[] graph = new HashSet[n + 1];
        for (int i = 0; i <= n; i++) graph[i] = new HashSet<>();
        for (int[] c : corridors) {
            int a = c[0], b = c[1];
            graph[a].add(b);
            graph[b].add(a);
        }

        for (int i = 0; i < n; i++) {
            dfs(graph, i, i, 1);
        }
        return res;
    }

    private void dfs(HashSet<Integer>[] graph, int cur, int start, int count) {
        // base case
        if (count == 3) {
            if (graph[cur].contains(start)) res++;
            return;
        }
        
        for (int next : graph[cur]) {
            if (next < cur) continue;
            dfs(graph, next, start, count + 1);
        }
    }
}
