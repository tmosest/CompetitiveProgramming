The blue rectangle above is included since the purple rectangle's intersection is subtracted twice! So we add the intersection once more to nullify this effect.

How do we come up with this during an interview?

It's not necessarily obvious how we might come to this conclusion, especially during an interview. Let's start by thinking about brute force approaches:

One most obvious solution that you probably came up with is attaining the sum manually each time by adding all values in the required range. As you might have also realised, this is quite inefficient. We know we would greatly benefit from precomputation. If we already understood the values of ALL the possible ranges, for example, we could just return that range when queried. This is probably not the solution, but it's a good start.

Interview tip: If you come across a brute force solution that performs a lot of repetitive tasks, consider DP and precomputation.

We've already ruled out the possibility of precomputing literally every possible range. So let's see if there's any way we can precompute values to get the range query some other way.

Interview tip: Think out loud! If you describe to your interviewer the brute force you've thought up and the inefficiencies of the brute force that could be improved, you're already doing great. Plus, it gives your interviewer the opportunity to give you better hints if you get stuck.

Now you start thinking about what else you can precompute:

  • Row and column sums
  • Partial ranges
  • etc...

Think about each possibility and how they might help you get an answer. From here, it's all about pattern recognition. But you've made your life a lot easier by breaking down the possibilities first and then thinking about patterns.

Interview tip: If you're still unable to think of anything, be sure to summarise your findings to your interviewer. Give them all the information they need and they might be able to nudge you in the right direction. Remember that they care a lot more about how you tackle the problem than whether you managed to miraculously come up with the solution in 1 minute.

As you can see, the best way to come up with an optimal solution is to not think of the optimal solution first. Think of brute force approaches, understand their flaws and work your way towards the gold. Hope this helps!

class NumMatrix {
    private int[][] sums;
    
    public NumMatrix(int[][] matrix) {
        int n = matrix.length;
        int m = matrix[0].length;
        sums = new int[n+1][m+1];
        for (int i=1; i<=n; i++)
            for (int j=1; j<=m; j++)
                sums[i][j] = sums[i-1][j] + sums[i][j-1] + matrix[i-1][j-1] - sums[i-1][j-1];
    }
    
    public int sumRegion(int row1, int col1, int row2, int col2) {
        int RED_RECTANGLE = sums[row2+1][col2+1];
        int PURPLE_RECTANGLES = sums[row1][col2+1] + sums[row2+1][col1];
        int BLUE_RECTANGLE = sums[row1][col1];
        return RED_RECTANGLE - PURPLE_RECTANGLES + BLUE_RECTANGLE;
    }
}

Understanding the Problem

Given a matrix matrix and many queries (row1, col1, row2, col2) (all inclusive), return the sum of all elements inside the rectangle whose top-left is (row1, col1) and bottom-right is (row2, col2).

Example used throughout:

matrix = [
  [3, 0, 1, 4, 2],
  [5, 6, 3, 2, 1],
  [1, 2, 0, 1, 5],
  [4, 1, 0, 1, 7],
  [1, 0, 3, 0, 5]
]
queries:
  (2,1,4,3) ? 8
  (1,1,2,2) ? 11
  (1,2,2,4) ? 12

Intuition

Prefix sum turns range sums into a couple of lookups.

  • 1D prefix: P[i] = a[0] + … + a[i-1] with P[0]=0. Then sum[l..r] = P[r+1] - P[l].
  • 2D prefix (padded): Build PS with an extra top row and left column of zeros so indices never go negative.

For a grid cell (i, j) (0-based in matrix):

PS[i+1][j+1] = matrix[i][j]
             + PS[i][j+1]      # top area
             + PS[i+1][j]      # left area
             - PS[i][j]        # overlap counted twice

A rectangle sum (r1,c1)..(r2,c2) then satisfies:

sum = PS[r2+1][c2+1] - PS[r1][c2+1] - PS[r2+1][c1] + PS[r1][c1]

Approach 0 : Naive

Idea: For every query, loop over all rows r ? [r1..r2] and columns c ? [c1..c2] and accumulate matrix[r][c].

Pseudocode

sumRegion(r1, c1, r2, c2):
    total = 0
    for r in r1..r2:
        for c in c1..c2:
            total += matrix[r][c]
    return total

Why it’s useful: Reveals the problem shape and the goal (repeat queries on static data).
Why it’s slow: O(area) per query; too slow for many large queries.

Approach 1

Row-wise Prefix Sum

In this approach, we build row-wise prefix sums first and then use them to answer submatrix sum queries. This is often the first idea that comes to mind before we move to the full 2D prefix sum.

Step 1: Build Row-wise Prefix Sums

  • For each row, compute prefix sums left to right.
  • Add a padding column of zeros at the beginning to simplify range queries.

Visual Representation:

Here:

  • Each entry represents the sum of elements in that row from column 0 up to current column.
  • The 0 padding ensures we can easily calculate differences without boundary issues.

Step 2: Answer Queries

To answer a submatrix sum query (r1, c1) -> (r2, c2):

  1. For each row r from r1 to r2:

    • Compute row contribution as prefix[r][c2+1] - prefix[r][c1].
    • This gives the sum of elements between c1 and c2 for that row.

  2. Add contributions of all rows.

Example Query: (2,1) -> (4,3)

  • Rows involved: 2, 3, 4.

  • Contribution breakdown:

    • Row 2: ps[2][4] - ps[2][1]
    • Row 3: ps[3][4] - ps[3][1]
    • Row 4: ps[4][4] - ps[4][1]

  • Final Answer = sum of all row contributions.

Visual Representation:

Here:

  • Colored regions show which rows are contributing.
  • Red line = c1 boundary, Blue line = c2 boundary.
  • Each row slice between red and blue lines is taken, then summed up.

Example Calculation (with numbers):

  • Row 2 ? ps[2][4] - ps[2][1] = 4 - 1 = 3
  • Row 3 ? ps[3][4] - ps[3][1] = 6 - 4 = 2
  • Row 4 ? ps[4][4] - ps[4][1] = 4 - 1 = 3

Final Answer = 3 + 2 + 3 = 8

Complexity

  • Preprocessing: O(R * C) for building row-wise prefix sums.
  • Query Time: O(R) per query (we iterate over each row in the query range).
  • Space: O(R * C) for storing prefix sums.

? Key Idea: Row-wise prefix sums simplify range queries but are slower for tall submatrices compared to full 2D prefix sums (Approach 2).

Advantages

? Simple to implement.
? Works well when queries are few and involve narrow column ranges.

Disadvantages

? Query time still linear in rows, not constant.
? Less powerful compared to full 2D prefix sum where queries become O(1).

public class NumMatrix {
    private readonly int[][] ps; // row-wise prefix with padding

    public NumMatrix(int[][] matrix) {
        int n = matrix.Length;
        if (n == 0) { ps = new int[0][]; return; }
        int m = matrix[0].Length;
        ps = new int[n][];
        for (int i = 0; i < n; i++) {
            ps[i] = new int[m + 1]; // ps[i][0] == 0
            for (int j = 0; j < m; j++) {
                ps[i][j + 1] = ps[i][j] + matrix[i][j];
            }
        }
    }

    public int SumRegion(int row1, int col1, int row2, int col2) {
        int sum = 0;
        for (int r = row1; r <= row2; r++) {
            sum += ps[r][col2 + 1] - ps[r][col1];
        }
        return sum;
    }
}

Approach 2

Full 2D Prefix Sum (Optimal — O(1) per query)

This approach pushes all heavy work into preprocessing by building a padded 2D prefix matrix PS. After that, any rectangle sum is answered in constant time with inclusion–exclusion.

Why 2D Prefix?

Row-wise prefix (Approach 1) still loops over rows for each query. A 2D prefix captures the sum of everything in the top-left rectangle for each cell, letting us subtract the parts we don’t want and add back the overlap — in O(1).

Padding idea: Create PS with an extra row and column of zeros: PS has shape (n+1) * (m+1). This avoids edge checks.

Step 1: Build the Padded 2D Prefix PS

For each matrix cell (i, j) (0-based in A), write to (i+1, j+1) in PS:

PS[i+1][j+1] = A[i][j]
             + PS[i][j+1]    # top rectangle (everything above)
             + PS[i+1][j]    # left rectangle (everything to the left)
             - PS[i][j]      # overlap counted twice

Key point: We always read already-built cells (up and left), so a simple row-major traversal suffices.

Visual: Building One 2D Prefix Cell

The three contributing prefix cells and the current matrix cell are highlighted. The padding row/col (index 0) makes borders trivial.

Step 2: Answer a Rectangle Sum via Inclusion–Exclusion

For a query (r1, c1) .. (r2, c2) (inclusive in A), map to PS with a (+1, +1) shift:

sum = PS[r2+1][c2+1]    # big prefix up to bottom-right
    - PS[r1][c2+1]      # remove rows above r1
    - PS[r2+1][c1]      # remove columns left of c1
    + PS[r1][c1]        # add back the overlap we subtracted twice

This is the 2D version of right - left in 1D, extended with an extra subtraction and an overlap add-back.

Visual: Inclusion–Exclusion for a Query

Green = big prefix up to (r2+1, c2+1); Red = the two strips we subtract (top and left); Blue = the overlap we add back; the dashed box shows the query area in PS coordinates (shifted by +1,+1).

Step 3: Walkthrough on the Running Example

Matrix A (same as Approach 1) and query (r1,c1,r2,c2) = (2,1,4,3).

From the built PS, pick the four cells:

  • PS[r2+1][c2+1] = PS[5][4] = 38 (big prefix)
  • PS[r1][c2+1] = PS[2][4] = 24 (top strip)
  • PS[r2+1][c1] = PS[5][1] = 14 (left strip)
  • PS[r1][c1] = PS[2][1] = 8 (overlap)

Combine:

sum = 38 - 24 - 14 + 8 = 8

Interpretation of the visual:

  • The green region is everything up to the query’s bottom-right corner.
  • The red regions remove what lies above and left of the query.
  • Their overlap (blue) was subtracted twice, so we add it back once.
  • The dashed rectangle marks the exact query rectangle in PS coordinates.

Complexity

  • Preprocessing: O(n · m)
  • Per query: O(1) (four lookups and three operations)
  • Space: O(n · m) for PS

Advantages

? Fastest queries — constant time per query.
? Clean indexing with padding; no branchy edge cases.
? Works beautifully for many queries on an immutable grid.

Disadvantages

? Slightly more memory than Approach 1 (though same asymptotics).
? Requires careful understanding of the (+1,+1) shift and inclusion–exclusion.

Key Idea

Precompute a padded 2D prefix so any rectangle sum is just big - top - left + overlap.

Code (Approach 2)

Each implementation builds a padded 2D prefix matrix PS of size (n+1) * (m+1) where PS[0][*] = PS[*][0] = 0.
Query (r1,c1)..(r2,c2) is answered in O(1) as:

PS[r2+1][c2+1] - PS[r1][c2+1] - PS[r2+1][c1] + PS[r1][c1]

public class NumMatrix {
    private readonly int[][] ps; // (n+1) x (m+1) padded 2D prefix

    public NumMatrix(int[][] matrix) {
        int n = matrix.Length;
        int m = (n == 0) ? 0 : matrix[0].Length;
        ps = new int[n + 1][];
        for (int i = 0; i <= n; i++) ps[i] = new int[m + 1];
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < m; j++) {
                ps[i + 1][j + 1] = matrix[i][j]
                                 + ps[i][j + 1]
                                 + ps[i + 1][j]
                                 - ps[i][j];
            }
        }
    }

    public int SumRegion(int row1, int col1, int row2, int col2) {
        return ps[row2 + 1][col2 + 1]
             - ps[row1][col2 + 1]
             - ps[row2 + 1][col1]
             + ps[row1][col1];
    }
}

Gotchas & Edge Cases

  • Empty matrix ? treat all sums as 0 (construct a 1*1 prefix of zeros).
  • Beware integer overflow on large inputs; use a wider type for PS if needed.
  • In code, prefer a padded structure ((n+1)*(m+1)) to avoid branchy edge cases.
  • In C#, jagged arrays (int[][]) tend to index a bit faster than rectangular (int[,]).

Wrap-Up

Idea:

This problem brings up one of the characteristics of a 2D matrix: the sum of the elements in any rectangular range of a matrix (M) can be defined mathematically by the overlap of four other rectangular ranges that originate at M[0][0].

The sum of the rectangle (0,0)->(i,j) is equal to the cell (i,j), plus the rectangle (0,0)->(i,j-1), plus the rectangle (0,0)->(i-1,j), minus the rectangle (0,0)->(i-1,j-1). We subtract the last rectangle because it represents the overlap of the previous two rectangles that were added.

With this information, we can use a dynamic programming (DP) approach to build a prefix sum matrix (dp) from M iteratively, where dp[i][j] will represent the sum of the rectangle (0,0)->(i,j). We'll add an extra row and column in order to prevent out-of-bounds issues at i-1 and j-1 (similar to a prefix sum array), and we'll fill dp with 0s.

At each cell, we'll add its value from M to the dp values of the cell on the left and the one above, which represent their respective rectangle sums, and then subtract from that the top-left diagonal value, which represents the overlapping rectangle of the previous two additions.

Then, we just reverse the process for sumRegion(): We start with the sum at dp[R2+1][C2+1] (due to the added row/column), then subtract the left and top rectangles before adding back in the doubly-subtracted top-left diagonal rectangle.

(Note: Even though the test cases will pass when using an int matrix for dp, the values of dp can range from -4e9 to 4e9 per the listed constraints, so we should use a data type capable of handling more than 32 bits.)

  • Time Complexity:
    • constructor: O(M * N) where M and N are the dimensions of the input matrix
    • sumRegion: O(1)
  • Space Complexity:
    • constructor: O(M * N) for the DP matrix
    • constructor: O(1) if you're able to modify the input and use an in-place DP approach
    • sumRegion: O(1)

Javascript Code:

The best result for the code below is 92ms / 43.3MB (beats 100% / 70%).

class NumMatrix {
    constructor(M) {
        let ylen = M.length + 1, xlen = M[0].length + 1
        this.dp = Array.from({length: ylen}, () => new Array(xlen).fill(0))
        for (let i = 1; i < ylen; i++)
            for (let j = 1; j < xlen; j++)
                this.dp[i][j] = M[i-1][j-1] + this.dp[i-1][j] + this.dp[i][j-1] - this.dp[i-1][j-1]
    }
    
    sumRegion(R1, C1, R2, C2) {
        return this.dp[R2+1][C2+1] - this.dp[R2+1][C1] - this.dp[R1][C2+1] + this.dp[R1][C1]
    }
};

Efficient 2D Range Sum Query Using Prefix Sum Matrix (Immutable Matrix)
Tharun__30
212

Java

Intuition

When faced with multiple queries asking for the sum of elements in a submatrix, recalculating the sum each time from the original matrix would be inefficient. To optimize this, we can preprocess the matrix to build a 2D prefix sum matrix that allows us to compute any submatrix sum in constant time.

Approach

  1. Preprocessing - Building the Prefix Sum Matrix:

  • We construct a prefix matrix where each element at (i, j) represents the sum of all elements in the submatrix from the top-left (0, 0) to (i, j) in the original matrix.

  • While filling the prefix matrix:

    • Add value from the original matrix.

    • Add top and left prefix values (if available).

    • Subtract the overlapping prefix value (top-left corner) to avoid double counting.

  1. Query - sumRegion(row1, col1, row2, col2):
  • To get the sum of a submatrix from (row1, col1) to (row2, col2), use the inclusion-exclusion principle:
  • sum = prefix[row2][col2]
    • prefix[row1 - 1][col2] [if row1 > 0]
    • prefix[row2][col1 - 1] [if col1 > 0]
    • prefix[row1 - 1][col1 - 1] [if both > 0]

Complexity

  • Time complexity:O(m*n)
  • Space complexity:O(m*n)

Code

Java
class NumMatrix {
    int[][] prefix;

    public NumMatrix(int[][] matrix) {
        prefix = new int[matrix.length][matrix[0].length];
        for (int i = 0; i < matrix.length; i++) {
            for (int j = 0; j < matrix[0].length; j++) {
                prefix[i][j] = matrix[i][j];
                if (i > 0) {
                    prefix[i][j] += prefix[i - 1][j];
                }
                if (j > 0) {
                    prefix[i][j] += prefix[i][j - 1];
                }
                if (i > 0 && j > 0) {
                    prefix[i][j] -= prefix[i - 1][j - 1];
                }
            }
        }
    }

    public int sumRegion(int row1, int col1, int row2, int col2) {
        int sum = prefix[row2][col2];
        if (row1 > 0) {
            sum -= prefix[row1 - 1][col2];
        }
        if (col1 > 0) {
            sum -= prefix[row2][col1 - 1];
        }
        if (row1 > 0 && col1 > 0) {
            sum += prefix[row1 - 1][col1 - 1];
        }
        return sum;
    }
}
