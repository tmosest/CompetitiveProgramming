Solution 1: Brute Force

Use a hashset seen to save all selected for beautiful array.

Python

    def minimumPossibleSum(self, n: int, target: int) -> int:
        seen = set()
        i = 1
        while len(seen) < n:
            if target - i not in seen:
                seen.add(i)
            i += 1
        return sum(seen)

Time O(n + target)
Space O(n)

Solution 2: a bit Math

k = target / 2 is the middle of taregt.
If n <= k,
we pick [1,2,3,...,n] as the beautiful array.
n + (n - 1) < k + k <= target,
so no problem,
the sum is n * (n + 1) / 2.

If n > k,
we pick [1,2,3,...,k] + [taregt, target + 1, .... , taregt + n - k - 1]
The sum of first part is k * (k + 1) / 2,
The sum of second part is (target + target + n - k - 1) * (n - k) / 2,

Time O(1), Space O(1)

Java

    public long minimumPossibleSum(int n, int target) {
        long k = target / 2;
        if (n <= k)
            return 1L * n * (n + 1) / 2;
        return k * (k + 1) / 2 + (target + target + n - k - 1) * (n - k) / 2;
    }

Approach

  • Iterate from 1 and keep on adding the number to a unorderd set, if the compliment of it (which k- i) is not already present in the set. Also add this to the answer as well.

C++

long long minimumPossibleSum(int n, int target) {
    set<int> st;
    long long ans = 0;
    for(int i = 1; st.size() < n; ++i ){
        if(st.find(target - i) == st.end()) { st.insert(i); ans += i; }
    }
    return ans;
}

Java

long minimumPossibleSum(int n, int target) {
    Set<Long> st = new HashSet<>();
    long ans = 0;
    for (long i = 1; st.size() < n; ++i) {
        if (!st.contains(target - i)) {
            st.add(i);
            ans += i;
        }
    }
    return ans;
}

Intuition

You can see in the question that we need to use pair sum of target. So we can just take one side of the pair and then move to target and add it from there.

Approach

Like for example lets take target as 50. Pairs that will add upto 50 will be
1 + 49
2 + 48
3 + 47
...
...
...
25 + 25
As we need minimum sum so we will consider sum of all pairs to the left hand side and then start from target as target will never have pairs (As negative integer are not to be consided).

Complexity

  • Time complexity: O(n)
  • Space complexity: O(1)

Code

class Solution {
    public long minimumPossibleSum(int n, int target) {
        long ans = 0;
        int i = 1;
        for(;i<=target/2 && i<=n;i++){
            ans += i;
        }
        int j = target;
        while(i<=n){
            ans += j;
            j++;
            i++;
        }
        return ans;
    }
}

class Solution {
    public long minimumPossibleSum(int n, int target) {
        int cur = 1;
        Set<Integer> set = new HashSet<>();
        long sum = 0;
        int i = 0;
        while(i < n) {
            if(set.contains(target-cur)) {
                cur++;
                continue;
            }
            sum+=cur;
            set.add(cur);
            i++;
            cur++;
        }
        return sum;
    }

Intuition

I initially tried to solve this problem using a HashSet.. trying all numbers up from 1 until I have found n smallest numbers that satisfy the anti "Two Sum" requirement via the hashset. This gave me Time Limit Exceeded. So I needed an approach that was faster than O(n) where n is the parameter "n." It would be great if I could find some range(s) where all of the elements lie instead of blindly incrementing upward.

Approach

I know that I want the smallest numbers possible so I will greedily take all numbers that I can starting from 1.

By symmetry across half the target (target/2) one can prove that if I take all numbers (1... floor(target/2)) I can no longer take any number in the range (target/2+1 ... target-1) since every number in my first range gets reflected over target/2 to find its complement that will have a sum of target.

For Example: consider a target of 6. I will choose numbers in the range (1...3) since 6/2=3. If I were to try to choose 4 now, 4 is reflected across 3 and on the other side we have 2. 2 (which we already chose) + 4 = 6. Therefore I cannot choose 4. The same can be said for all elements in that first range of (1...target/2) they all have reflections onto the range (target/2+1, target-1) and so this reflected range is now invalid. What is another range that I can choose from?

Well, we know that we have already optimally picked all the smallest numbers below the target. The other range lies on the other side of target. In fact, every element >= target is a viable candidate since any natural number + (a number >= target) will be greater than target (never equal to target) so my second range starts with target and increments up until I have chosen my set of n numbers. The great thing about these two ranges is that they both are arithmetic sequences which means that I can use calculus to solve the resultant summations of these sequences in O(1) time.

for the first range: from 1 to target/2 inclusive (or any upperbound number for that matter), the equation is simply: upperBound * (upperBound+1) / 2. The second range is slightly more difficult because the lower bound is not 1. For a sequence that starts at a number greater than 1 (and ours will-- it will start at target in fact,) the equation is (the summation of numbers from 1 to upper bound) - the summation of numbers from 1 to lowerbound-1. Since we have transformed this summation into two summations that both are lowerbound by 1, we can apply the same formula as we did for the first range's summation.

The last difficult part of the problem is making sure that when doing arithmetic with big numbers, we must prevent overflow carefully via using the given MOD and I also used a Long data type at one point.

Complexity

  • Time complexity:

O(1) There are no loops or recursion in this code. Pure math for the win.

  • Space complexity:

There are no data structures in this code aside from ints and longs. Space does not scale up for bigger input sizes. Therefore:
O(1)

Code

Java
class Solution {
    public int minimumPossibleSum(int n, int target) {
        int MOD = 1_000_000_007;

        // Compute the number of values that can be taken from the first range
        int half = target / 2;
        int countLow = Math.min(n, half); //maybe we dont even need all elements in this first range!

        // Sum of the first `countLow` integers
        long lowSum = ((long) countLow * (countLow + 1) / 2) % MOD;

        // Remaining numbers to include
        int remainingCount = n - countLow;

        // If we need more numbers, they start from `target`
        long start = target;
        long end = target + remainingCount - 1;

        // Sum of the range [start, end]
        long highSum = (end * (end + 1) / 2) % MOD - ((start - 1) * start / 2) % MOD;

        // Ensure the result of subtraction is non-negative
        if (highSum < 0) {
            highSum += MOD;
        }

        // Total sum modulo MOD
        return (int) ((lowSum + highSum) % MOD);
    }
}
