Approach 1: DFS

Intuition

This problem is essentially a dependency resolution problem. We need to determine which recipes we can create based on our initial supplies and the possibility of creating intermediate recipes. This is a perfect fit for a depth-first search (DFS) approach, as we need to explore each recipe's dependencies recursively.

The key insight is to model this as a graph problem:

  • Nodes are recipes and supplies
  • Edges represent "ingredient-of" relationships
  • We need to detect cycles (recipes that depend on each other)

Approach

  1. Convert the supplies list to a set for O(1) lookup
  2. Create a dictionary (hash map) mapping each recipe to its ingredients
  3. Use DFS to determine if we can make each recipe:
    • If the ingredient is a basic supply, we can make it
    • If the ingredient is another recipe, recursively check if we can make it
    • Use a visited dictionary to track recipe states and detect cycles
    • When we finish processing a recipe successfully, add it to the result

The visited dictionary uses three states:

  • 0: Currently visiting (in progress) - helps detect cycles
  • 1: Successfully visited (can make)
  • -1: Cannot make

Complexity

  • Time complexity: O(N + E) where N is the number of recipes and E is the total number of ingredients across all recipes.
  • Space complexity: O(N + S) where N is the number of recipes and S is the number of supplies.

class Solution:
    def findAllRecipes(self, recipes: List[str], ingredients: List[List[str]], supplies: List[str]) -> List[str]:
        available_supplies = set(supplies)
        
        recipe_to_ingredients = {recipes[i]: ingredients[i] for i in range(len(recipes))}
        
        visited = {}
        result = []
        
        def can_make(recipe):
            if recipe in visited and visited[recipe] == 0:
                return False
                
            if recipe in visited and visited[recipe] == 1:
                return True
                
            if recipe in available_supplies:
                return True
                
            if recipe not in recipe_to_ingredients:
                return False
                
            visited[recipe] = 0
            
            for ingredient in recipe_to_ingredients[recipe]:
                if not can_make(ingredient):
                    visited[recipe] = -1
                    return False
                    
            visited[recipe] = 1
            result.append(recipe)
            return True
        
        for recipe in recipes:
            can_make(recipe)
        
        return [recipe for recipe in recipes if recipe in visited and visited[recipe] == 1]

Approach 2: Topological sort (Khan's algorithm)

Intuition

This problem can also be elegantly solved using Khan's algorithm for topological sorting. The key insight is to view the problem as a dependency graph where:

  • Supplies and recipes are nodes
  • Directed edges go from ingredients to the recipes that use them
  • A recipe can only be made when all its dependencies (ingredients) are satisfied

Khan's algorithm is particularly well-suited for this problem because it processes nodes in order of their dependencies being satisfied, which matches exactly how we would create recipes in real life.

Approach

  1. Build a graph representation:
    • Track the in-degree (number of ingredients needed) for each recipe
    • For each ingredient, maintain a list of recipes that depend on it
    • Map each recipe to its list of ingredients
  2. Initialize a queue with all available supplies
  3. Process the queue using Khan's algorithm:
    • For each item (supply or recipe) in the queue:
      • If it's a recipe, add it to our result
      • For all recipes that depend on this item, decrease their in-degree
      • If a recipe's in-degree reaches zero (all ingredients available), add it to the queue
  4. Return the list of recipes we were able to make

This approach handles the cyclic dependencies naturally - if recipes depend on each other in a cycle, their in-degree will never reach zero, and they won't be added to the queue.

Complexity

  • Time Complexity: O(V + E) where V is the number of vertices (recipes + supplies) and E is the number of edges (ingredient relationships). Each vertex and edge is processed exactly once.

  • Space Complexity: O(V + E)

class Solution:
    def findAllRecipes(self, recipes: List[str], ingredients: List[List[str]], supplies: List[str]) -> List[str]:
        available_supplies = set(supplies)
        
        ingredient_to_recipes = {}
        
        in_degree = {}
        
        recipe_to_ingredients = {}
        
        for i, recipe in enumerate(recipes):
            recipe_ingredients = ingredients[i]
            recipe_to_ingredients[recipe] = recipe_ingredients
            in_degree[recipe] = len(recipe_ingredients)
            
            for ingredient in recipe_ingredients:
                if ingredient not in ingredient_to_recipes:
                    ingredient_to_recipes[ingredient] = []
                ingredient_to_recipes[ingredient].append(recipe)
        
        queue = list(available_supplies)
        result = []
        
        while queue:
            current = queue.pop(0)
            
            if current in recipe_to_ingredients:
                result.append(current)
            
            if current in ingredient_to_recipes:
                for dependent_recipe in ingredient_to_recipes[current]:
                    in_degree[dependent_recipe] -= 1
                    
                    if in_degree[dependent_recipe] == 0:
                        queue.append(dependent_recipe)
        
        return result

Before we hit that DFS giga-brain strat, let’s talk about the OG way: Brute Force (BFS vibes). No thinking, no optimizing—just monkey? brain checking every single recipe one by one until we figure out what’s cookable. A true skibidi approach ??

Brute Force Plan (BFS - Bread First Search ?)

  • Start with what we got – Supplies? We take those.
  • Iterate like a bot – For each recipe, check if all ingredients exist in our supplies.
  • Keep adding to the stash – If we can cook a recipe, add it to supplies and loop again.
  • Run this loop until we ain’t cookin’ no more.

Complexity

  • Time complexity: O(N * M), Where N is the number of recipes and M is the average number of ingredients per recipe.

  • Space complexity: O(N+M)

class Solution {
public:
    vector<string> findAllRecipes(vector<string>& recipes, vector<vector<string>>& ingredients, vector<string>& supplies) {
        set<string> available(supplies.begin(), supplies.end());  // Stash of what we got
        unordered_map<string, vector<string>> needs;  // Recipe ? Required Ingredients

        for (int i = 0; i < recipes.size(); i++)
            needs[recipes[i]] = ingredients[i];

        bool updated = true;
        while (updated) {  // Keep going until we can't make anything new
            updated = false;
            for (auto& r : recipes) {
                if (available.count(r)) continue;  // Already made
                
                bool canMake = true;
                for (string& ing : needs[r]) {
                    if (!available.count(ing)) {  // Missing ingredients? Nah, ain't cookin' that.
                        canMake = false;
                        break;
                    }
                }
                
                if (canMake) {
                    available.insert(r);  // We made it! Add to supplies
                    updated = true;
                }
            }
        }
        
        vector<string> res;
        for (auto& r : recipes) if (available.count(r)) res.push_back(r);
        return res;
    }
};

class Solution {
public:
    map<string, vector<string>> adj;
    map<string, bool> visited;
    set<string> avail;
    map<string, bool> memo;

    bool dfs(string curr){
        if(avail.count(curr)) return true;
        // if(visited[curr]) return true;
        if(memo.count(curr)) return memo[curr];

        if(adj.find(curr) == adj.end()) return false;
        memo[curr] = false;
        for(auto &i : adj[curr]){
            if(!dfs(i)) return false;
        }

        avail.insert(curr);
        return memo[curr] = true;
    }
    vector<string> findAllRecipes(vector<string>& recipes, vector<vector<string>>& ingredients, vector<string>& supplies) {
        int n = recipes.size();

        for(int i=0; i<n; i++){
            for(string &j: ingredients[i]){
                adj[recipes[i]].push_back(j);
            }
        }

        // for(auto &str: supplies){
        //     visited[str] = true;
        // }

        for(auto &str : supplies){
            avail.insert(str);
        }

        vector<string> res;
        for(auto &st : recipes){
            if(dfs(st)){
                res.push_back(st);
            }
        }
        return res;

Topological Sort

Intuition

The problem can be modeled as a graph problem where:

  • Each ingredient and recipe are nodes.
  • A directed edge exists from an ingredient to a recipe if that recipe requires the ingredient.
  • We need to find all recipes that can be made starting from the given supplies.

Since some recipes depend on others, we can use Topological Sorting (Kahn’s Algorithm) via BFS to solve this problem.

Approach

  1. Graph Construction

    • Create a graph where each ingredient points to the recipes that require it.
    • Maintain an in-degree map to count how many ingredients are needed for each recipe.
    • Convert supplies into a set for quick lookup.

  2. BFS (Kahn’s Algorithm for Topological Sorting)

    • Start with all available supplies in a queue.
    • Process each item in the queue:
      • If it’s an ingredient in the graph, reduce the in-degree of dependent recipes.
      • If a recipe's in-degree becomes 0, add it to the result and queue (as it can now be used as a supply).

  3. Return the list of all possible recipes.

Complexity

  • Time Complexity: (O(N + E))

    • (N) = number of recipes
    • (E) = total number of dependencies (ingredients)
    • Each node and edge is processed at most once.

  • Space Complexity: (O(N + E))

    • Storing the graph and in-degree map requires extra space.

import 'dart:collection';

class Solution {
  List<String> findAllRecipes(List<String> recipes, List<List<String>> ingredients, List<String> supplies) {
    Map<String, List<String>> graph = {}; // ingredient -> list of recipes
    Map<String, int> indegree = {};       // recipe -> number of ingredients needed
    Set<String> available = Set.from(supplies);
    List<String> result = [];

    // Step 1: Initialize graph and indegree
    for (int i = 0; i < recipes.length; i++) {
      String recipe = recipes[i];
      indegree[recipe] = ingredients[i].length;

      for (String ing in ingredients[i]) {
        graph.putIfAbsent(ing, () => []).add(recipe);
      }
    }

    // Step 2: Queue for BFS starting from available supplies
    Queue<String> queue = Queue.from(supplies);

    while (queue.isNotEmpty) {
      String item = queue.removeFirst();
      if (graph.containsKey(item)) {
        for (String next in graph[item]!) {
          indegree[next] = indegree[next]! - 1;

          if (indegree[next] == 0) {
            // All ingredients available, recipe can be made
            result.add(next);
            queue.add(next); // This new recipe is now a supply
          }
        }
      }
    }

    return result;
  }
}

Why This Approach?

? Graph-based approach: Represents dependencies effectively.
? Topological Sorting (Kahn’s Algorithm): Ensures correct order of recipe preparation.
? Efficient BFS Traversal: Ensures we process each node only once.
