Since all elements are unique and within [1..n], we can represent our tree as intervals.

We start with [1..n] interval, and the depth of that interval is 0. When we insert, say, 3, we split that interval into two: [1..2] and [4..n], and increment their depth. For any value, we can quickly find it's interval using binary search.

The picture below demonstrates how we split intervals for this test case: [3,5,1,2,6,7,4]

To model this logic, we can use a map to store numbers and their depth. When we insert a new number, we first find the insert position (O(n log )). Then, we get the depth of numbers on the left and right (our interval). Finally, we insert a new value, and its depth is the maximum depth of the neighbours, plus 1.

C++

int maxDepthBST(vector<int>& order) {
    map<int, int> m{{0, 0}, {100001, 0}};
    for (int i : order) {
        auto it = m.upper_bound(i);
        m[i] = 1 + max(it->second, prev(it)->second);
    }
    return max_element(begin(m), end(m), [](const auto& a, const auto &b){ return a.second < b.second; })->second;
}

Java

public int maxDepthBST(int[] order) {
    TreeMap<Integer, Integer> m = new TreeMap<>();
    for (int i : order) {
        Map.Entry<Integer, Integer> l = m.floorEntry(i), r = m.ceilingEntry(i);
        m.put(i, 1 + Math.max(l == null ? 0 : l.getValue(), r == null ? 0 : r.getValue()));
    }
    return m.entrySet().stream().max((a, b) -> a.getValue().compareTo(b.getValue())).get().getValue();
}

This also works with standard bisect_left; it's just faster with sortedcontainers.

class Solution:
    def maxDepthBST(self, order: List[int]) -> int:
        from sortedcontainers import SortedList
        sl, d = SortedList([0, 100001]), { 0 : 0, 100001 : 0 }
        for i in order:
            j = sl.bisect_left(i)
            d[i] = 1 + max(d[sl[j - 1]], d[sl[j]])
            sl.add(i)
        return max(d.values())

Solution 0 - The Naive Approach:

One obvious way to do this would be to define a node class, and just construct the binary tree from there. At every insertion, we can just record the number of nodes taken to reach the bottom. Simple enough, right?

However, there's a very clear weakness to this approach (and binary search trees in general, if they are not self-balancing). If you insert the elements in order, the tree becomes extremely unbalanced! This pretty much turns the tree into a linked list, which turns your normally desirable time complexity O(log n) into O(n) for insertions. Coupled with the constraint that n can reach all the way to 10?, this O(n2) approach is just begging to run into a TLE.

I coded up this approach anyway, just to give a test. Sure enough, this approach doesn't work, failing on test case 66 out of 70. I won't put the test case explicitly here, but it exploits the weakness we just found earlier. I'm sure you can figure out what that looked like.

So, how do we remedy this?

There are a few nice hints from the problem description. First of all, the input array is a permutation of the numbers from 1 through n, guaranteeing that we won't have duplicate elements. Since our BST only needs to support insertion, we know that the depths will not change after being added either. Both of these reduce our workload considerably.

Now, how do we avoid the issues with our naive, unbalanced tree?

Solution 1 - TreeMaps with Indexes:

Let's consider what we're really interested in when we insert a new element into our tree. Let's say we've put the values [6, 2, 1, 8] so far into our tree and we're trying to put in a 4 next. If we've rigged up our binary tree right, this is what we should be looking at:

In this case, 4 is a direct child of 2. One important observation here is that, in terms of order, we only care about the elements that are directly next to 4, because those are the only nodes that could possibly be parents. We couldn't care less about 8 or 1 for that matter.

So here, the nextdoor nodes are 2 and 6. From here, it's easy to tell which is the actual parent: it's the one with the greatest depth! Since we're using a TreeMap, we are able to associate each value in the tree with its depth, so this lookup can happen without much penalty. Hence, node 4 must be a child of 2 because it has a greater depth. The depth of node 4 is then simply 1 greater than its parent's.

As a side note, it's guaranteed that the depths of the parents must be different. See if you can convince yourself why!

Finding the nextdoor nodes isn't too tricky. We can utilize floorEntry() and ceilingEntry() to retrieve their depths in guaranteed O(log n) time. This gives us an overall time complexity of O(n * log n). Furthermore, the TreeMap itself requires O(n) space to maintain.

Here's my (commented) code in Java. Try it yourself first!

class Solution {
    public int maxDepthBST(int[] order) {
        int n = order.length, maxDepth = 1;
        
        // our map will associate a value in our BST to its depth
        TreeMap<Integer, Integer> map = new TreeMap<>();
        map.put(order[0], 1);
        
        for (int i = 1; i < n; i++) {
            int val = order[i];
            
            // getting left and right nextdoor entries! (and their corresponding depths)
            Map.Entry<Integer, Integer> left = map.floorEntry(val);
            Map.Entry<Integer, Integer> right = map.ceilingEntry(val);
            int leftDepth = 0, rightDepth = 0;
            
            if (left != null) leftDepth = left.getValue();
            if (right != null) rightDepth = right.getValue();
            
            // the depth of our value is the highest of the two, plus one (since it's a child)
            int depth = Math.max(leftDepth, rightDepth) + 1;
            maxDepth = Math.max(maxDepth, depth);
            
            map.put(val, depth);
        }
        return maxDepth;
    }
}

There are certainly optimizations to make here, but the code here is relatively simple so I've decided to keep it this way. The actual performance of this code is fairly modest, with a runtime of 430ms along with 48MB of memory use.

Solution 2: TreeMaps with Intervals:

If we change up our view of the problem, we can arrive at an (albeit similar) approach which utilizes intervals instead. Let's have a look! (Also where credit is due - thanks votrubac for the insight! Do check out his C++ solution as well.)

First off, let's return to our original example from before with the input [6, 2, 1, 8, 4, ...] Starting at the beginning, no matter which node we insert, the tree will have a depth of 1. After we put our first value, 6, into the tree, the next node can either be below or above 6 (since we have no duplicates). In either of these cases, the tree will have a maximum depth of 2. We can then continue this process, keeping track of the depths of each potential interval. We can do this because we already know the range of the values put into the tree, which is just equal to its length (as seen from earlier).

How do we turn this into an algorithm? Perhaps this visualization might help.

We always start off with a single interval spanning the entire array. Then, when we go and insert a value N into our tree:

  1. We search for the relevant interval containing our value in the TreeMap.
  2. This interval is split at N, giving us at most two sub-intervals.
  3. We add 1 to the depths of the sub-intervals before putting them back into our TreeMap.

Here, the TreeMap is again used because it can keep our intervals sorted, so our lookup also occurs in O(log n) time. This again yields a solution with a runtime of O(n * log n). As with before, our TreeMap utilizes O(n) space.

Keep in mind that we don't need to store the entire interval into our TreeMap! It's much easier if we simply store the starting indexes of each interval. When we do our binary search, we can invoke floorEntry() to find the interval containing our target value.

Anyways, you're welcome to try out this solution if you'd like! Here's my code, also in Java:

class Solution {
    public int maxDepthBST(int[] order) {
        int n = order.length, maxDepth = 1;
        
        // now, these are the smallest values (inclusive) for each interval:
        TreeMap<Integer, Integer> map = new TreeMap<>();
        map.put(1, 0);
        
        for (int i = 0; i < n; i++) {
            int val = order[i];
            
            // we're looking for the greatest value below our queried value:
            Map.Entry<Integer, Integer> lowBound = map.floorEntry(val);
            int bound = lowBound.getKey();
            int depth = lowBound.getValue() + 1;
            
            maxDepth = Math.max(depth, maxDepth);
			
			if (bound < val - 1)
				map.replace(bound, depth);
			
            map.put(val, depth);
        }
        
        return maxDepth;
    }
}

This code is moderately faster, with a runtime of 358 ms while using 48.1 MB of memory. It's because we're able to optimize the number of searches we do through the tree: specifically, we'll only update the depth of the bound if there will be more elements between the bound and our queried value.

You could decrease the runtime further if you physically implemented each interval, whether that's through a simple 2-element array or your own custom-defined class, because it'll let you make further optimizations on the number of searches through the tree that you'll need. I'll leave that for you to implement if you're up for the challenge :)
